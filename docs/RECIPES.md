# 通用配方规划

配方用于把一组已知参数展开成多张表的显式请求。编译不读取业务记录、不挑选当前 ID、不发批准，也不执行写入。模板只做 JSON 数据替换，不执行 Python、Shell 或表达式。

定义放在 `config/recipes/`。`parameters` 为参数名到 `{type,required,default}` 的映射，支持 string、int、number、bool、array、object。整项 `{{name}}` 保留参数类型；嵌在文本里的占位符只接受标量。未知参数、缺参、类型不符、重复步骤、未知依赖或循环依赖会阻断编译。

每个步骤声明 `name`、`request` 和可选的 `depends_on`。request 与 `Workflow.preview` 接收的请求一致；示例见 `config/recipes/example_batch.json`。计划有摘要并绑定项目 ID 和根名称，修改后需要重新编译。输出目录必须位于表格数据根之外。

执行顺序是：编译 → 选择当前步骤 → 重新读取实际来源并预览 → 人工确认 → apply → 回读通过 → 生成下一步当前预览。前一步已写入后，同一本 Excel 的旧预览可能已失效，因此不能把编译时生成的所有预览直接当作后续有效凭据。

当前规划器给出拓扑顺序，但没有自动推进或自动审核整批事务的执行器。调用方必须保存每步真实回执并按依赖执行。需要强制跨步队列、统一审批或跨表补偿时，先设计并测试对应状态机，再接入现有预览和逐表事务，不能把依赖名存在 JSON 中当作已经具备这些能力。

扩展配方时优先修改数据模板。仅当现有 patch/append 无法表达业务行为时，才新增 operation；完整链路与测试要求见 EXTENDING.md。
