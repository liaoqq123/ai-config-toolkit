# 怎样补充知识与完善工具

先判断缺少的是数据、证据还是能力。补一条说明、登记一个引用和增加一个可执行写入操作，是三种不同的工作。

## 选择正确的修改层

|缺项|应修改的位置|完成条件|
|---|---|---|
|新增数据根、状态位置|项目配置|路径可解析，状态不在源目录内|
|表头位置或有效区协议|受支持的layout配置|隔离样表的身份、字段与有效区解释正确|
|一个表的用途、操作说明|知识notes或其Markdown来源|有来源、无当前值冒充真值，查询可命中|
|别名或业务选表导航|项目aliases/知识节点与边|目标明确，歧义保留，不猜依赖|
|引用关系|表头声明或显式references协议|类型、路径、条件与证据明确，能校验当前引用|
|新的JSON引用机制|项目扩展与专用验证器|路径枚举、反例、预览和回读均通过|
|新业务操作|operation适配与执行链|从输入到恢复都有实现与回归|
|新存储格式|格式适配器|schema、读取、渲染、预览和回读覆盖完整|
|运行性能问题|缓存/索引实现|不绕过来源变化与审批绑定，实测改进|

如果只是新增一张表，不要为表名增加一个通用引擎 `if` 分支。优先复用实际表头和已支持的类型、主键、引用协议。

如果只是组合现有 patch/append，请先按 `RECIPES.md` 扩展数据模板。模板编译与依赖排序已经提供，但自动推进、整批审批和跨表补偿尚未提供，不能只新增几个参数就宣称这些能力已实现。本机逐表确认的实际边界见 `REVIEW.md`。

## 补充 schema 与格式知识

读取实际文件与分表，保存真实逻辑表身份、字段、类型、约束和来源指纹。来源索引保留结构，不长期缓存业务行作为未来任务的现值。

表头异常先解释并保留证据。例如两个字段同名，不能通过“默认取后者”掩盖；只有精确、可验证的适配规则才能改变解析。新的例外必须限定到该格式或项目，附正反 fixture，不能悄悄扩成通用行为。

公式表达式、共享公式和缓存值分开记录。读到缓存不能证明已经重算；未知公式不通过复制一个历史值解决。

## 补充别名与业务映射

别名是经过确认的另一种名称，不是模糊匹配后自动选择的目标。说明别名指向逻辑表、文件范围还是具体分表；多目标时必须保留全部候选。

业务映射只告诉查询“可能从哪些节点开始”。例如“目录分组”可以导航到 Catalog 与 Groups，但不表示本次改一个 Count 就要修改 Groups，也不表示应复制所有分组记录。

增加映射后检验：自然语言能找到正确节点，精确 ID 查询不被其他节点正文污染，返回的来源不会静默合并不同根中的同名表。

知识节点的 `sources` 是数据来源坐标；单数 `source` 是正文 Markdown 文件，两者用途不同。正文采用内联 `content` 或 `source` 二选一，并至少包含一个 Markdown 标题，否则构建会明确报错。比如将下面的节点放入 notes，并在该知识 JSON 旁的 `notes/catalog-guide.md` 写完整 Markdown：

```json
{
  "id": "rule:catalog-guide",
  "kind": "rule",
  "title": "目录维护说明",
  "group": "人工规则",
  "aliases": ["目录维护"],
  "source": "notes/catalog-guide.md",
  "sources": [
    {"root": "demo", "file": "Catalog.xlsx", "sheet": "配置", "table": "Catalog"}
  ]
}
```

这里的 `root` 对应根目录演示配置中的 `demo`。换到其他项目时使用该项目定义的根名称，不能照抄。边的 `source` 和 `target` 则是已存在 notes 节点的 ID，不是 Markdown 路径。

## 补充引用证据

每条引用至少说明：来源逻辑表与字段/JSON路径、目标逻辑表与主键、适用条件、空值/哨兵语义，以及证据出处。

|证据类型|可以推出的结论|
|---|---|
|真实表头 FOREIGN|字段被声明为引用；实际记录仍需核对|
|显式项目配置|项目维护者登记的契约；需验证与实际格式一致|
|经过测试的适配器|所限定输入和条件下的程序语义|
|业务选表导航|查询候选；不自动构成引用或写入闭包|
|人工推断|待验证假设，不能直接驱动写入|

对复杂 JSON，必须明确哪些字符串是 ID、哪些是标签或枚举，是否支持数组、键引用、条件分支、嵌套包和循环。没有证据的字段保留未知，不按 `id`、`reward` 或 `group` 的名字猜目标。

## 补充手工规则与未知项

每条规则回答：适用范围是什么、证据来自哪里、何时核对过、有哪些例外、哪些仍未知。虚构示例可以是：

```markdown
# Catalog 分组规则

适用：Catalog.xlsx 的“配置”分表，真实A1为Catalog。

已知：GroupId表头声明FOREIGN:Groups.Id。当前引用存在性由定向读取核对。

依据：本项目来源索引及实际第6行约束。

未知：分组在应用中的显示顺序尚无实现或运行证据。

处理：可以校验GroupId存在，不能据此修改应用排序或猜测启用方式。
```

业务文档与程序契约同步前，规则仍只是说明。不要把“写进了笔记”当作引擎已经支持。

## 更新知识库而不覆盖人工内容

1. 定位知识源文件、输入节点 ID 和当前生成章节。使用 `read` 查看现有全文。
2. 更新原Markdown来源或notes配置中的内容，保留人工补充与未知项。不要只改生成文件后期待下一次构建自动理解其来源。
3. 对用户直接编辑的合集章节和卷级说明，先读取并合并，保留工具的编辑保护；不能清空状态索引来绕过保护。
4. 运行 build、query、read、validate，核对正文、属性、章节链接与原节点身份。
5. 记录来源变化与更新范围。旧归档保留在项目状态的 `knowledge-archive/`，仓库内只展示当前合集。

若当前生成内容和源资料不一致，先对照现有章节及编辑记录，再决定更新哪个来源。不要一律以“自动生成”为由覆盖用户修改。

输入 notes 或 Markdown 是作者源。某节一旦有直接的人工修改，后续 source 更新不会自动覆盖它；先协调现有节与作者源中的差异。不要删除状态索引来解除编辑保护。

## 注册一个新的 operation

当前 `patch` 和 `append` 是已有能力。增加例如 `rename_id` 之类的操作，必须完成以下接口链；这个名称仅作设计例子，不是现有命令。

1. 输入：定义必需字段、允许范围、目标身份、版本和歧义处理；拒绝未知键与不完整请求。
2. 依赖：显式列出读取来源及为什么需要；ID更名不能只改主表而忽略引用。
3. 校验：定义类型、主键、引用、公式与结构边界；收集实际前值。
4. 预览：输出完整具体差异、依赖指纹、风险或未解决项；对不了解的目标不可生成可执行预览。
5. 登记：接入 workflow 的 operation 解析与分发，并保持原来的审批、来源CAS、备份和锁边界。
6. 写入：只修改预览允许的内容；新操作不得直接调用文件保存绕过统一事务。
7. 回读：从保存后的实际文件重新解析，验证目标值、依赖和非目标内容。
8. 恢复：说明能自动撤回的状态以及遇到外部编辑时如何安全停止。
9. 交付：更新合法示例、能力矩阵、CLI帮助和下面的隔离回归。

跨文件业务操作还需明确执行顺序、部分完成的处理和事务边界。多个单表 apply 成功并不等于拥有跨文件原子提交能力。

## 怎样写有意义的测试

使用临时目录和完全虚构的工作簿。fixture 从脚本构造，不复制真实业务表或历史审批。

|变更|最低回归|
|---|---|
|路径解析|移动工作区、配置相对路径、非法数据根、状态落入源目录被拒绝|
|表头/有效区|边界行、重复主键、重复字段、空主键、非导出列|
|引用|有效目标、缺失目标、多个同名来源、预览后依赖变化|
|patch|正常改值、错误前值、公式保护、非目标XML与成员保真|
|append|完整字段、新主键冲突、有效区边界、尾部内容与已有公式保留|
|事务|目标变化、依赖变化、重复审批、并发归属、写入或回读失败与安全恢复|
|知识合编|属性/全文往返、唯一章节、链接迁移、人工章内/章外编辑保留|
|查询/read|精确别名、分页、单节读取、不把整卷正文赋给每个节点|

不要用只复述实现分支的测试代替用户可观察结果。真实来源CAS、回读和非目标内容检查比“函数被调用过”更有价值。

## 文档也需要跟着扩展

改能力就更新 `ARCHITECTURE.md` 的矩阵；改操作顺序就更新 `OPERATING_MODEL.md`；改新项目接入就更新 `PROJECT_ONBOARDING.md`；改节点或引用协议就更新合法配置样例与知识示例。

完成时给下一位 AI 一个可执行的验收入口和一个明确反例，说明遇到哪些输入仍会拒绝。未实现的业务、格式或自动化保持明确边界，不把后续建议写成当前支持。
