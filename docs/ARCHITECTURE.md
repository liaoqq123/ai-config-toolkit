# 架构、契约与能力边界

## 数据流

```text
项目配置 → 数据根与格式profile → 定向读取/结构索引
                          ├→ 知识节点与证据边 → 合集/查询/单节读取/校验
                          └→ patch或append请求 → 预览 → 用户确认 → 审批记录
                                                               ↓
                                  来源及依赖CAS → 备份/journal → 写入 → 回读/回执
```

知识库和写入引擎在来源身份与项目设置上对齐，不能用知识库“存在一条关系”代替真实记录引用检查。

## 模块职责

|职责|公开入口或协议|不应混入什么|
|---|---|---|
|项目定位|`config_toolkit.core.project.load_project(path)`|真实项目的默认路径和隐藏回退根|
|Excel结构与数据|`config_toolkit.core.excel.build_index(...)`、`read_table(...)`|按业务名猜字段语义|
|预览与写入|`config_toolkit.core.workflow.Workflow(project, root_name)`|未经预览和确认的隐式业务动作|
|配方规划|`config_toolkit/tools/config_plan.py`|自动选取现值、自动确认或推进后续写入|
|本机确认页|`client/review_server.py`|公网认证、企业审批连接或自动apply|
|知识构建|`config_toolkit/tools/knowledge.py build`|当前业务值的长期缓存|
|知识定位|`query`、`read`|把整卷内容混入每个节点的搜索文本|
|知识校验|`validate`|将链接正确误当业务配置已生效|
|项目语义|项目配置、规则文档、经过测试的扩展|在通用模块里增加真实表名分支|

实现位于 `config_toolkit/core/`，脚本入口位于 `config_toolkit/tools/`。项目配置应通过同一个 Project 实例传递，不能从 CLI 中取得一套根目录、在适配器里又拼出另一套目录。

## 项目对象

`load_project(path)` 返回 Project。调用方应复用它解析路径，避免各模块自行解释相对路径。

|属性或方法|职责|
|---|---|
|`path`|实际加载的项目配置文件|
|`config`|经过校验的项目配置|
|`project_id`|独立的项目身份|
|`state_dir`|该项目的草稿、事务、备份和运行产物位置|
|`root(name)`|解析显式命名的数据根|
|`resolve_config_path(value)`|按配置文件位置解析资源路径|
|`layout`|当前明确支持的表头与有效区协议|

状态目录不能位于任何配置数据根内。不能通过使用相同 `project_id` 把另一个目录中的旧状态伪装为当前项目状态。

## Excel协议

布局 profile 描述行号、A1 逻辑表位置和有效区标记。本包演示采用多行表头，但这只是一个受支持的格式协议。

通用字段校验负责真实表头、主键、基础类型和已声明引用。额外业务语义需要配置或适配器；未知公式、复杂约束和不支持的工作簿结构必须明确拒绝或提出补充要求。

读取工作簿结构与保存工作簿是不同能力。能显示某个单元格，不表示可以安全重写其公式、关系、绘图、宏或其他 archive 成员。

当前 patch 保守拒绝直接覆盖公式、合并单元格或多格公式范围。append 需要已有、无公式的记录行作为样式模板；带有效区尾部内容、合并区域、Excel表格、数据验证、筛选和条件格式等范围控制结构时会拒绝，必须先实现布局适配器。无标记或独立空End行等不同格式不能因为读取成功就假定可以追加。

## 预览与执行契约

每份预览必须绑定项目、数据根、物理目标、操作、记录差异和来源指纹，并包含验证所用依赖的快照信息。审批绑定该预览，不能只绑定文件名或一句“同意修改”。

执行时重新核对目标和依赖。即使目标文件未变，引用字典或其他验证来源发生变化，也可能使旧预览失效。不要只对待写文件做 CAS。

回执应来自真实回读，描述实际保存的位置与验证结果。预览成功、审批成功、提交成功、回读成功是不同状态。

## 知识模型

知识输入由节点和证据边构成。一个节点有稳定 ID、标题、别名、类别、分组以及正文或 Markdown 来源。边指出来源节点、目标节点和证据；业务映射只表达候选导航，不默认提升为写入依赖。

合集是展示层。合编后多个节点可以共享一个文件，但各自的章节、原属性、正文和搜索文本必须独立。路径字段保持纯文件路径，章节另存；不能把 `#章节` 拼进一个随后交给文件系统读取的路径。

人工章节修改与卷级补充都要保留。构建先读取现有内容、检查来源变化、验证逐节往返，再更新生成内容；旧归档放到 `state_dir/knowledge-archive/`，不在仓库内继续堆放旧 Markdown。

## 分阶段能力矩阵

|阶段|当前能力|需要新增实现才能做到|
|---|---|---|
|项目定位|显式配置、多个命名根、独立状态|其他配置格式、组织级项目发现|
|数据读取|受支持profile的xlsx结构索引与定向记录读取|任意Excel布局、非xlsx存储|
|基础写入|已有表的显式patch与append|任意工作表结构迁移、工作簿重建|
|执行保护|预览、审批、来源及依赖CAS、备份、回读与恢复|跨文件原子提交、分布式事务|
|确认界面|仅本机逐表展示和人工批准|自动apply、企业身份验证、外部审批集成|
|知识库|显式节点/边、全文合编、查询、单节读取、校验|自动证明业务语义、客户端运行验收|
|业务编排|通用参数模板、依赖排序、显式请求编译和单步预览|自动推进、整批自动批准、领域闭包、业务激活、多阶段业务事务|
|其他格式|清晰的扩展位置和fixture要求|自定义格式的解析、预览、写入和回读适配器|

不要把右列写成当前功能清单。增加一项业务能力，需要贯穿输入协议、依赖展开、验证、预览、审批、写入、回读和测试。

通用模板与依赖顺序见 `RECIPES.md`；本机人工确认、批准绑定和执行边界见 `REVIEW.md`。编译成功不表示每步当前预览仍有效，前一步写入后应重新生成下一步预览。

## 扩展边界

配置可以改变位置与明确声明；代码负责算法与执行保障。适配器负责项目特有语义，不能绕过通用执行边界。

每个新增 operation 至少定义输入结构、作用范围、读取依赖、可解释差异、允许改动的 archive 成员、回读方法和恢复条件。仅向命令枚举增加名称不会产生一项完整能力。
